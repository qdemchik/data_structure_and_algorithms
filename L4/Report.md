
# Отчёт по лабораторной работе №4
**Вариант:** 8

## Цель работы
Освоить сортировки с гарантированной оценкой $O(n \log n)$ и линейно-временные сортировки; научиться сопоставлять их свойства (время, память, стабильность, ограничения применимости) и выбирать алгоритм по характеру данных.

## Задание
1. Реализовать MergeSort, CountingSort, RadixSort (LSD) и HeapSort.
2. Выполнить бенчмарк всех четырёх алгоритмов против QuickSort (из ЛР 3) и встроенного `sorted()` на 5 классах входов.
3. Составить сводную таблицу свойств алгоритмов.
4. Провести верификацию реализаций по 4-шаговой методике.

## Теоретические сведения
- **Нижняя оценка:** Любая сортировка сравнением требует $\Omega(n \log n)$ операций в худшем случае (доказывается через высоту дерева решений $\ge \log_2(n!)$).
- **MergeSort:** Стабильная, гарантированно $O(n \log n)$, требует $O(n)$ доп. памяти.
- **CountingSort:** Линейная $O(n + k)$, стабильная. Применима только при малом диапазоне ключей $k$.
- **RadixSort (LSD):** Линейная $O(d \cdot (n + b))$, стабильная. Требует устойчивой внутренней сортировки по разрядам.
- **HeapSort:** Нестабильная, $O(n \log n)$, работает in-place ($O(1)$ памяти), но имеет плохую локальность кэша.

## Реализация алгоритмов
- **MergeSort:** Реализован рекурсивно. Стабильность обеспечена условием `left[i] <= right[j]` при слиянии (при равенстве ключей элемент из левой половины берётся первым).
- **CountingSort:** Реализован устойчивый вариант с префиксными суммами. Ключевой момент: проход по исходному массиву выполняется **с конца** (`reversed(a)`), что гарантирует сохранение относительного порядка равных элементов.
- **RadixSort LSD:** Реализован поверх устойчивой CountingSort по десятичным разрядам (основание $b=10$). Отрицательные числа обрабатываются через временное смещение (`offset`).
- **HeapSort:** Реализован in-place. Построение кучи выполняется просеиванием вниз (`sift_down`) от последнего нелистового узла (`n // 2 - 1`) к корню, что гарантирует сложность построения $O(n)$.

## Результаты верификации
Верификация проведена по методике `docs/ai-verification.md`:
1. **Инварианты:** Реализованы проверки `is_sorted` (неубывающий порядок) и `same_multiset` (совпадение счётчиков элементов через `collections.Counter`).
2. **Репрезентативные тесты:** Успешно пройдены тесты на пустом массиве, массиве из 1 элемента, массиве с одинаковыми элементами, уже отсортированном и обратно отсортированном входах.
3. **Сравнение с эталоном:** Проведено 300 запусков на случайных входах (включая отрицательные числа и дубликаты). Расхождений с `sorted()` не выявлено.
4. **Оценка сложности:** Бенчмарки подтвердили теоретические оценки. *Примечание:* стандартный QuickSort из ЛР 3 падал с `RecursionError` на входе с множеством дубликатов (`random_small`). Дефект был локализован и исправлен путём внедрения 3-частного разбиения (Dutch National Flag), после чего повторная верификация прошла успешно.

## Результаты бенчмарков
Замеры проводились на размерах $n \in [1000, 100000]$, 5 повторов, медиана.

| Алгоритм | Случайный (широкий) | Случайный (узкий) | Отсортированный | Обратный | Почти отсортированный |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **MergeSort** | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ |
| **CountingSort** | *Пропуск* ($k=10^9$) | **$O(n)$** (самый быстрый) | $O(n)$ | $O(n)$ | $O(n)$ |
| **RadixSort** | $O(n \log_{10}(\max))$ | $O(n)$ | $O(n)$ | $O(n)$ | $O(n)$ |
| **HeapSort** | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ |
| **QuickSort** | $O(n \log n)$ | $O(n)$ (3-way) | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ |
| **sorted()** | Быстрее всех (Timsort на C) | Быстрее всех | **$O(n)$** (1 серия) | $O(n \log n)$ | $O(n)$ |

*Графики:* Построены log-log графики зависимости времени от $n$. Наклон линий MergeSort, HeapSort и QuickSort близок к 1 (что соответствует $O(n \log n)$ на логарифмической шкале), в то время как CountingSort на узком диапазоне показывает почти горизонтальную линию (линейный рост).

## Выводы
1. **Стабильность MergeSort** обеспечивается условием `<=` при слиянии. Если заменить на `<`, порядок равных элементов нарушится.
2. **Ограничение CountingSort:** Время и память $O(n + k)$. При $k \gg n$ (например, ключи до $10^9$) алгоритм теряет смысл из-за гигантских затрат памяти на массив счётчиков.
3. **Устойчивость RadixSort:** Внутренняя сортировка по разрядам обязана быть устойчивой. Если она неустойчива, она разрушит порядок, корректно выстроенный на предыдущих шагах по младшим разрядам.
4. **Нестабильность HeapSort:** Обмен корня кучи с последним элементом при извлечении максимума переносит элемент на большое расстояние, «перепрыгивая» через равные элементы и нарушая их исходный порядок.
5. **Обход нижней оценки:** CountingSort и RadixSort не являются сортировками сравнением. Они используют значение ключа как индекс массива, работая в другой вычислительной модели, поэтому граница $\Omega(n \log n)$ на них не распространяется.
